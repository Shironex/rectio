title: Skins

A skin changes how the interface is set, not what colour it is: the type scale, line heights,
heading face, corners, border width and weight, spacing and control sizes, and how surfaces float
(translucency, an edge highlight, a hard offset shadow). It is a set of token overrides applied
with `data-skin` on any element, so every component, block and template follows with no code of
its own. Colour stays with the theme, so a skin works in light and dark and with any theme,
including one from the [theme generator](/docs/theming/generator).

## The skins

| Skin        | For                                              | What it sets                                                                                                                                                                                                                                                  |
| ----------- | ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `dense`     | Data-heavy apps: finance, admin, monitoring      | 13px body text, tighter line heights, 3px controls and 6px panels, a 3.5px spacing unit, 24, 32 and 36px controls                                                                                                                                             |
| `editorial` | Reading surfaces, reports, marketing pages       | IBM Plex Serif headings and amounts, hairline borders (0.5px: one device pixel on 2x screens, 1px on 1x), 2px corners, looser line heights, a roomier rhythm                                                                                                  |
| `glass`     | Dashboards and consumer apps over rich backdrops | Cards and block panels at 85% opacity, popups, dialogs, sheets, toasts and the app header the same over a 20px backdrop blur, a 1px light edge along their top, a wide soft shadow, 8px controls and 16px panels, a wash of blue and cyan tints in the canvas |
| `brutalist` | Tools and pages that want to look built          | Two pixel borders in the text colour, square corners, hard 4px offset shadows (6px for popups and dialogs) instead of soft ones, one step heavier type                                                                                                        |

Glass and brutalist are opt-in looks: nothing in the kit, its docs previews or its templates turns
them on unless you set the attribute.

Each ships as its own registry item. Install one, then set the attribute:

```sh
pnpm dlx @rectio/cli add skin-editorial
```

```html
<html data-theme="default" data-mode="dark" data-skin="editorial"></html>
```

`rectio init --skin <id>` adds a skin while setting up a project. The CLI imports a skin after your
themes and before the base styles.

## Where it applies

`data-skin` works like the other theming attributes: on `<html>` for the whole app, or on any
element for one part of the page. [`ThemeScope`](/docs/components/theme-scope) takes it as a prop,
and popups opened inside the scope keep it.

```tsx
<ThemeScope skin="dense">
  <Dashboard />
</ThemeScope>
```

It composes with everything else:

- **Light and dark.** A skin sets no colour, so `data-mode` and the system colour scheme keep
  working, and every contrast check the theme passes still holds. The token tests run the full
  contrast and colour vision suite for each skin in both modes anyway.
- **A theme inside it.** A skin wins over a theme on the same element and over any `data-theme`
  inside it.
- **Skins inside skins.** The nearest skin wins: a `ThemeScope skin="editorial"` on a dense page
  is editorial, and so is everything in a plain `<div data-skin="editorial">`, at any depth.
- **Turning a skin off.** `skin="none"` on a ThemeScope (or `data-skin="none"` beside a
  `data-theme`) stops the skin around it: the subtree shows the theme's own type, corners and
  rhythm. A ThemeScope with no `skin` keeps the skin around it.
- **Compact density.** `data-density="compact"` applies on top of a skin, inside it or around it.
- **Reduced motion.** Motion belongs to the theme and to reduced motion, never to a skin.
- **Touch.** Controls keep their 44px hit area on touch screens in every skin. Where a skin widens
  the border, fields and table rows grow by the extra width, so the steppers and sort headers inside
  them stay 44px.

## Glass

Glass makes surfaces translucent. The ones that float over content (popovers, menus, selects, date
pickers, dialogs, the command menu, sheets, toasts and the sticky app shell header) also blur what is
behind them. Cards and block panels sit in the page, so they let the canvas through with no blur:
scrolling content never blurs. Each pane casts a wide soft shadow, drawn in the theme's scrim
colour. The page canvas (a ThemeScope or an AppShell) picks up pools of the theme's blue and cyan
identity tints at its top corners and its foot, so the panes have colour to show.

- **Solid where it has to be.** The translucent layer applies only where the browser supports
  `backdrop-filter` and the person has not set `prefers-reduced-transparency: reduce`. Everywhere
  else the same surfaces stay solid, with the edge highlight and the rounder corners, so glass never
  lets sharp text through a pane.
- **Reduced transparency where the browser reports it.** Only some browsers (Chromium based ones
  today) report `prefers-reduced-transparency`; elsewhere a person who asked for less transparency
  in their system still sees the panes translucent. The contrast floor below holds there too: body
  and muted text keep 4.5:1 on a pane over any backdrop.
- **Readable text.** The contrast and colour vision tests hold every pair on the solid fallback, the
  same as any skin. On top of that, the translucent surfaces are tested against the backdrop glass
  is made for: every text and mark pair holds AA over each page surface of its mode and over the
  washed canvas, and body and muted text keep 4.5:1 over any backdrop at all, pure black and pure
  white included.
- **The assumption.** Over a photo, a video or a saturated fill, subtle text and small marks on a
  pane can drop under AA. Put a scrim under the pane there, or turn the skin off for that region
  with `skin="none"`.
- **One element at a time.** Only the surface itself turns see-through; a sticky row or a field
  inside it stays solid on its own fill, and so does a surface inside another one (a card in a card,
  a card in a dialog).

## Brutalist

Brutalist draws edges: every border and divider in the text colour at two pixels, square corners,
and a hard offset shadow under raised and floating surfaces in place of the soft one. Body text is
set one weight heavier.

- **Focus stays visible.** A focus outline paints over the element's own shadow. Each theme draws
  the offset shadow in its own colour, set apart from its focus colour: the tests hold the focus
  ring at 3:1 against the shadow as well as against the canvas, in light and dark, and the theme
  generator corrects a generated theme the same way.
- **Fields follow.** Inputs and selects take the ink edge through `--rx-field-border`, and tinted
  badges take their edge in the full tone through `--rx-badge-edge`.
- **Disabled reads apart.** A disabled control keeps the theme's plain border (`border-line-disabled`)
  while enabled ones are inked, so it is told apart by its edge, not by its text colour alone.

## Dense or compact

Both make a screen tighter, at different scales:

|               | `data-density="compact"`                                                     | `data-skin="dense"`                                        |
| ------------- | ---------------------------------------------------------------------------- | ---------------------------------------------------------- |
| Changes       | Spacing unit, control, row and header sizes                                  | Type scale and line heights, corners, spacing and controls |
| Typical scope | One region: a table, a side panel                                            | The whole app                                              |
| Together      | Inside dense: same control heights, a smaller spacing unit and large padding | Dense leaves room for compact below it                     |

Reach for compact when one working area needs more rows on screen; reach for dense when the whole
product is a tool people read numbers in all day.

On touch screens both keep controls at their 44px hit area, so dense shows most on desktop,
where a pointer allows smaller targets.

## The skin contract

A skin may override these token groups and nothing else. The token build fails on anything outside
them, and on a token the theme does not define.

| Group               | Tokens                                                                                                                                                            |
| ------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Type                | `--rx-font-family-*`, `-size-*`, `-line-height-*`, `-weight-*`, `-tracking-*`                                                                                     |
| Shape               | `--rx-radius-*`, `--rx-border-width`, `--rx-border-ink`                                                                                                           |
| Rhythm and controls | `--rx-space-unit`, `--rx-control-height-*`, `--rx-control-padding-x-*`                                                                                            |
| Surfaces            | `--rx-surface-blur`, `--rx-surface-wash`; in a translucent layer only, `--rx-surface-opacity` and `--rx-surface-backdrop`                                         |
| Shadows             | `--rx-shadow-highlight`, `--rx-shadow-ambient`, `--rx-shadow-offset-raised`, `--rx-shadow-offset-overlay`; `--rx-shadow-raised` and `-overlay` only to clear them |
| Component           | Non-colour component tokens, such as `--rx-emphasis-style` or `--rx-tree-indent`                                                                                  |

The surface and shadow tokens are switches: plain numbers and lengths, the same in light and dark.
What they turn on (the edge highlight colour `--rx-border-highlight`, the offset shadow colour
`--rx-shadow-offset-color`, the scrim under the ambient shadow, the tints of the wash) belongs to the theme and is defined in each of
its modes, so a dark scope inside a light page keeps its own colours. Colour and motion are never
part of a skin, a skin never draws a shadow of its own, and neither is a touch height
(`--rx-control-height-touch` and every `*-touch` token): touch targets stay 44px in every skin.
Amounts stay tabular in every skin. Editorial sets them in the serif through `--rx-money-family`,
which keeps tabular lining figures, so columns still line up; other figures, such as chart axes,
keep the theme's numeric face.

## Your own skin

A skin is two CSS rules. Copy `styles/rectio/skins/dense.css` after adding it, rename the id in
its selectors and change the values, and import the file after your themes. The first rule sets the
values on the skin and on a theme on the same element, so it beats the theme. The second lets a
theme inside the skin (a ThemeScope, say) take the same tokens back from around it with `inherit`;
that is what makes the nearest skin win when skins nest, so list every token of the first rule in it.

```css
[data-skin='roomy'],
[data-skin='roomy'][data-theme] {
  --rx-space-unit: 0.3rem;
  --rx-radius-panel: 0.75rem;
  --rx-popover-radius: var(--rx-radius-panel);
  --rx-dialog-radius: var(--rx-radius-panel);
}

[data-skin='roomy'] :where([data-theme]:not([data-skin])) {
  --rx-space-unit: inherit;
  --rx-radius-panel: inherit;
  --rx-popover-radius: inherit;
  --rx-dialog-radius: inherit;
}
```

A component token that reads a token you change (such as `--rx-button-radius`, which reads
`--rx-radius-control`) has to be declared in the rule again, as the shipped skins do: a CSS variable
keeps the value it had where it was declared. `none` is taken: it turns a skin off.

Your own components follow a skin through the token utilities. Two utilities are the hooks the
glass skin reaches: `backdrop-surface` on a surface that floats over content (it takes the skin's
translucency and blurs what is behind it), `translucent-surface` on a surface in the page (the same
translucency, no blur), and `canvas-wash` on a page canvas. All three do nothing in a theme, and a
surface inside another one stays solid. `cn` treats them as a background image and a backdrop
filter, so a `bg-[url()]` or `backdrop-blur-*` class you pass replaces them. Shadows follow through `shadow-raised` and `shadow-overlay`, `shadow-panel` on a flat panel
(nothing in a theme; the edge highlight and the ambient shadow where a skin sizes them) and
`shadow-indicator` on a thumb or a selected segment inside a track (no offset or ambient layer to
spill out of it). A translucent skin of your own puts its opacity and backdrop in a third rule, inside
`@supports (backdrop-filter: blur(1px))`, and sets them back to `1` and `none` under
`@media (prefers-reduced-transparency: reduce)`, as `styles/rectio/skins/glass.css` does.

The [theme generator](/docs/theming/generator) previews any theme under each skin.
