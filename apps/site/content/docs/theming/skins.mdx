title: Skins
description: Dense and editorial looks on top of any theme, light or dark, through data-skin.

A skin changes how the interface is set, not what colour it is: the type scale, line heights,
heading face, corners, border width, spacing and control sizes. It is a set of token overrides
applied with `data-skin` on any element, so every component, block and template follows with no
code of its own. Colour stays with the theme, so a skin works in light and dark and with any theme,
including one from the [theme generator](/docs/theming/generator).

## The skins

| Skin        | For                                         | What it sets                                                                                                                                                 |
| ----------- | ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `dense`     | Data-heavy apps: finance, admin, monitoring | 13px body text, tighter line heights, 3px controls and 6px panels, a 3.5px spacing unit, 24, 32 and 36px controls                                            |
| `editorial` | Reading surfaces, reports, marketing pages  | IBM Plex Serif headings and amounts, hairline borders (0.5px: one device pixel on 2x screens, 1px on 1x), 2px corners, looser line heights, a roomier rhythm |

Each ships as its own registry item. Install one, then set the attribute:

```sh
pnpm dlx @rectio/cli add skin-editorial
```

```html
<html data-theme="default" data-mode="dark" data-skin="editorial"></html>
```

`rectio init --skin <id>` adds a skin while setting up a project. The CLI imports a skin after your
themes and before the base styles.

## Where it applies

`data-skin` works like the other theming attributes: on `<html>` for the whole app, or on any
element for one part of the page. [`ThemeScope`](/docs/components/theme-scope) takes it as a prop,
and popups opened inside the scope keep it.

```tsx
<ThemeScope skin="dense">
  <Dashboard />
</ThemeScope>
```

It composes with everything else:

- **Light and dark.** A skin sets no colour, so `data-mode` and the system colour scheme keep
  working, and every contrast check the theme passes still holds. The token tests run the full
  contrast and colour vision suite for each skin in both modes anyway.
- **A theme inside it.** A skin wins over a theme on the same element and over any `data-theme`
  inside it.
- **Skins inside skins.** The nearest skin wins: a `ThemeScope skin="editorial"` on a dense page
  is editorial, and so is everything in a plain `<div data-skin="editorial">`, at any depth.
- **Turning a skin off.** `skin="none"` on a ThemeScope (or `data-skin="none"` beside a
  `data-theme`) stops the skin around it: the subtree shows the theme's own type, corners and
  rhythm. A ThemeScope with no `skin` keeps the skin around it.
- **Compact density.** `data-density="compact"` applies on top of a skin, inside it or around it.
- **Reduced motion.** Motion belongs to the theme and to reduced motion, never to a skin.
- **Touch.** Controls keep their 44px hit area on touch screens in every skin.

## Dense or compact

Both make a screen tighter, at different scales:

|               | `data-density="compact"`                                                     | `data-skin="dense"`                                        |
| ------------- | ---------------------------------------------------------------------------- | ---------------------------------------------------------- |
| Changes       | Spacing unit, control, row and header sizes                                  | Type scale and line heights, corners, spacing and controls |
| Typical scope | One region: a table, a side panel                                            | The whole app                                              |
| Together      | Inside dense: same control heights, a smaller spacing unit and large padding | Dense leaves room for compact below it                     |

Reach for compact when one working area needs more rows on screen; reach for dense when the whole
product is a tool people read numbers in all day.

On touch screens both keep controls at their 44px hit area, so dense shows most on desktop,
where a pointer allows smaller targets.

## The skin contract

A skin may override these token groups and nothing else. The token build fails on anything outside
them, and on a token the theme does not define.

| Group               | Tokens                                                                           |
| ------------------- | -------------------------------------------------------------------------------- |
| Type                | `--rx-font-family-*`, `-size-*`, `-line-height-*`, `-weight-*`, `-tracking-*`    |
| Shape               | `--rx-radius-*`, `--rx-border-width`                                             |
| Rhythm and controls | `--rx-space-unit`, `--rx-control-height-*`, `--rx-control-padding-x-*`           |
| Component           | Non-colour component tokens, such as `--rx-emphasis-style` or `--rx-tree-indent` |

Colour, shadow and motion are never part of a skin, and neither is a touch height
(`--rx-control-height-touch` and every `*-touch` token): touch targets stay 44px in every skin.
Amounts stay tabular in every skin. Editorial sets them in the serif through `--rx-money-family`,
which keeps tabular lining figures, so columns still line up; other figures, such as chart axes,
keep the theme's numeric face.

## Your own skin

A skin is two CSS rules. Copy `styles/rectio/skins/dense.css` after adding it, rename the id in
its selectors and change the values, and import the file after your themes. The first rule sets the
values on the skin and on a theme on the same element, so it beats the theme. The second lets a
theme inside the skin (a ThemeScope, say) take the same tokens back from around it with `inherit`;
that is what makes the nearest skin win when skins nest, so list every token of the first rule in it.

```css
[data-skin='roomy'],
[data-skin='roomy'][data-theme] {
  --rx-space-unit: 0.3rem;
  --rx-radius-panel: 0.75rem;
  --rx-popover-radius: var(--rx-radius-panel);
  --rx-dialog-radius: var(--rx-radius-panel);
}

[data-skin='roomy'] :where([data-theme]:not([data-skin])) {
  --rx-space-unit: inherit;
  --rx-radius-panel: inherit;
  --rx-popover-radius: inherit;
  --rx-dialog-radius: inherit;
}
```

A component token that reads a token you change (such as `--rx-button-radius`, which reads
`--rx-radius-control`) has to be declared in the rule again, as the shipped skins do: a CSS variable
keeps the value it had where it was declared. `none` is taken: it turns a skin off.

The [theme generator](/docs/theming/generator) previews any theme under each skin.
